1. Introduction

1.1 Purpose

This Software Architecture Document (SAD) provides a complete architectural overview of the Island Rental System, a full-stack booking platform for island destinations, hotels, and tours. It records the significant architectural decisions, layering strategy, and role-based access model that govern the system, and is intended for developers, reviewers, and maintainers who need to understand how the platform is structured end-to-end — from the React client through the Express API to the MariaDB persistence layer.

1.2 Scope

The scope of the Island Rental System covers a React 18 + TypeScript single-page client application, a RESTful Express.js API server, and a relational MariaDB/MySQL database (schema islan_tour) served locally through XAMPP. The system allows public visitors to browse islands, hotels, and tours; allows registered users to create and manage bookings and payments; and allows administrators to manage the entire catalog, bookings, users, and payment records through a dedicated admin console. Native mobile clients, third-party payment gateway integration, and multi-tenant deployment are explicitly out of scope for this architecture.

3. Architectural Goals and Constraints

3.1 Technical Goals & Objectives

  1. Clean Client/Server Decoupling: The React SPA communicates with the backend exclusively over a versioned JSON REST API, never accessing the database directly.
  2. Role-Based Access Enforcement: System features and API routes are gated by user role (public, protected user, admin) at the middleware level.
  3. Booking Lifecycle Integrity: Every booking is created with a server-computed total price and a controlled status lifecycle, preventing client-side price tampering.
  4. Session Security: Authentication uses signed JWTs so the server remains stateless between requests.
  5. Type Safety: Shared TypeScript types (types/index.ts) keep the client's data shapes aligned with the API contract.

3.2 System Constraints

  • Fixed Technology Stack: React 18 + TypeScript on the client, Express.js on Node.js for the API, and MariaDB/MySQL for persistence.
  • Local Development Topology: The client runs on port 3000, the API server on port 5001, and MariaDB 10.4.32 on port 3306 via XAMPP.
  • Stateless Authentication: Sessions are not stored server-side; the JWT (HS256) issued at login is the sole proof of identity, held client-side in localStorage.
  • Styling Constraint: All UI styling is implemented with Tailwind CSS utility classes; no separate CSS-in-JS or SCSS pipeline is used.

3.3 Design Rationale

Architectural Rationale: Separating the system into three independently deployable layers (React client, Express API, MariaDB store) connected only through well-defined HTTP/JSON and SQL contracts keeps each layer independently testable and replaceable. Using a raw mysql2 connection pool instead of an ORM keeps SQL explicit and predictable while express-validator centralizes input validation at the route boundary.

5. Logical View

5.1 Overview — Three-Tier Layering

The system follows a strict three-tier architecture with a clear boundary between client, API, and database.

Figure 5.1 — System Architecture at a Glance (Layered View with Modules)

5.2 Frontend Layer

Pages & Routes are grouped by access tier:

  • Public: Home, Islands, IslandDetail, Hotels, Tours
  • Auth: Login, Register
  • Protected (user): Dashboard, BookingPage
  • Admin: AdminDashboard, Bookings, Islands, Hotels, Tours, Rooms, Users, Payments

Layouts & Guards: Layout and AdminLayout wrap their respective route trees; ProtectedRoute and AdminRoute guard access based on AuthContext state. UI libraries in use include react-hook-form, react-hot-toast, lucide-react, and tailwindcss.

5.6 Middleware & Configuration

  • Auth Middleware: protect verifies the JWT; authorize('admin') checks the decoded role.
  • JWT Strategy: HS256 signing, token read from the Authorization header, persisted client-side in localStorage.
  • Validation: express-validator chains (body / param / query) run before controller logic.
  • Config: config/database.js exposes the mysql2 pool; cors, helmet, and morgan are applied as global middleware.

6. Process View

6.1 Authentication Flow

Figure 6.1 — Authentication Sequence Diagram
  1. User POSTs credentials to /api/auth/login.
  2. authController queries the users table; bcrypt verifies the password hash.
  3. Server signs an HS256 JWT containing user.id and role, and returns it.
  4. Client stores the token in localStorage and sets AuthContext state.
  5. The Axios interceptor injects Authorization: Bearer <token> on every subsequent request.
  6. The protect middleware verifies the token; authorize('admin') checks the role where required.

6.2 User Booking Flow

Figure 6.2 — Booking Creation Sequence Diagram
  1. User navigates to /booking/hotel/:id or /booking/tour/:id.
  2. BookingPage computes a live total from selected dates × price_per_night (or per-person price for tours).
  3. The form submits to bookingsAPI.createBooking().
  4. bookingController re-fetches the authoritative hotel/tour price server-side, recomputes the total, and validates the dates.
  5. A row is inserted into bookings; status defaults to pending.
  6. A toast confirms success and the client redirects to /dashboard.

6.3 Admin Booking Creation Flow

  1. Admin clicks "New Booking"; a slide-in panel opens.
  2. The panel fetches users, hotels, and tours in parallel on open.
  3. Admin selects a guest, booking type, hotel/tour, and dates; a live price preview updates.
  4. A POST is sent to /api/bookings/admin/create with user_id in the body.
  5. createAdminBooking runs behind the authorize('admin') guard.
  6. The row is inserted into bookings; the admin table auto-refreshes via fetchBookings().

6.4 Concurrency Model

The API server runs on Node.js's single-threaded event loop with non-blocking I/O. Database access is pooled through mysql2/promise, allowing multiple concurrent requests to share a bounded set of MariaDB connections without blocking the event loop.

7.2 Execution Modes & Environment Requirements

  • Development Mode: The React dev server (npm start, port 3000) proxies API calls to the Express server (node server.js / nodemon, port 5001).

8.2 Layers

  1. Presentation Layer (React SPA): Pages and components under client/src/, styled with Tailwind CSS utility classes, communicating exclusively through services/api.ts.
  2. REST Controller & Middleware Layer (Express): Routes dispatch to controllers; protect/authorize('admin') enforce access before controller logic runs; express-validator validates request bodies.
  3. Data Access Layer (mysql2): Controllers issue parameterized SQL through the shared pool in config/database.js, avoiding SQL injection and ORM overhead.

9.2 Data Integrity Rules

Rule 1 — Server-Computed Price: total_price is always computed by bookingController from the authoritative price_per_night or tour price, never trusted from client input.
Rule 2 — Exclusive Booking Target: A booking references exactly one of hotel_id or tour_id based on booking_type; the other FK column remains NULL.
Rule 3 — Default Pending Status: New bookings and payments default to pending status and progress through admin-controlled transitions (e.g. pending → confirmed → completed or cancelled).
Rule 4 — Referential Integrity: rooms.hotel_id, hotels.island_id, tours.island_id, and every FK in bookings/payments/reviews reference their parent table with foreign key constraints enforced by MariaDB.

10. Size and Performance

The chosen architecture targets responsive local and small-deployment performance for a booking-oriented workload:

  • Concurrent Users: Comfortably supports 100–200 concurrent browsing/booking sessions on a single API instance backed by a pooled mysql2 connection.
  • Catalog Query Latency: Average island/hotel/tour listing queries respond in < 50 ms under normal load.
  • Booking Transaction Time: Booking creation (price computation + insert) completes in < 300 ms end-to-end.
  • Client Bundle: Production React build stays under ~500 KB gzipped through code-splitting of admin routes.

11. Quality

11.1 Security

  • Password Security: Passwords are hashed with bcrypt before storage; plain-text passwords are never persisted.
  • Session Authenticity: HS256 JWTs carry user.id and role; every protected route runs through the protect middleware.
  • SQL Injection Immunity: All queries use parameterized statements via mysql2.
  • Transport Hardening: helmet sets protective HTTP headers; cors restricts allowed origins.

11.2 Maintainability

  • MVC Separation: Routes, controllers, and middleware are cleanly separated, keeping each file focused on one responsibility.
  • Centralized Validation: express-validator chains keep input rules declarative and consistent across routes.
  • Type Safety: Shared TypeScript types keep the client and API contract aligned as the schema evolves.

11.3 Reliability

  • Connection Pooling: The mysql2 pool automatically recovers dropped connections without restarting the API process.
  • Graceful Auth Failure: The Axios interceptor redirects to /login on 401 responses rather than leaving the UI in a broken state.
  • Request Logging: morgan logs every request, aiding post-incident diagnosis.
